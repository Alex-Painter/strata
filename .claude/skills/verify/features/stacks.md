# Stacks

A stack is a group of PRs whose branches feed into each other. The reviewer gives Strata one PR or branch and gets the whole stack around it as a Change, or browses every stack in a repo and opens one. In the workspace, a Change pane at the left (drag its edge to resize it; collapse it to a strip) lists Whole stack and the layers, then draws the stack's pull requests as a graph, each with its title and head branch; the stack list's cards show the stack map (tips on top, the trunk at the bottom, merged PRs included). Choosing a PR scopes the page to it ("How it arrived"). A stack that forks has one path, and one Change, per tip, with a path picker to move between them. Each scope has its diff, the whole-stack diff or the PR's own (with a banner when GitHub's diff of the PR differs), and choosing a layer shows that layer's files and hunks. The whole stack's overview shows Claude's summary, then the Guide (the order to read it in), then the layers; the layer by PR matrix is behind Display. A PR shows what it changes. Without Claude, the Guide is Strata's own groups and the notes in the Change pane's details say why there's no summary.

## Sub-features

- `stack-list`: `/repos/<owner>/<name>` lists the repo's stacks, newest activity first, each with its map and an Analyse button, which makes the path's Change and runs it. `#stack-<root>` scrolls to that stack.
- `stack-map`: on each stack list card. Every PR links to GitHub, merged PRs link to the commit they landed as, and an open PR that needs a restack has a dashed edge and says so (a merged or closed one can't be restacked, so it doesn't).
- `pr-scope`: choosing a PR in the sidebar shows its branches, how it sits on its parent with commit evidence, where its own changes start, and its issues. The URL gets `?pr=<n>`.
- `path-picker`: in the workspace, the Pull requests graph at the left of the main pane draws the whole stack, with each PR's head branch under its title; on a fork, the other branch's PRs are dimmed and choosing one opens that path's Change. The stack list's cards still have a picker.
- `diffs`: a layer's view lists its files by path, each with its hunks under it; big files start closed and mechanical ones folded. The whole stack shows the whole-stack diff; a PR shows its own, says when Strata replayed it onto the stack below, and shows a `GitHub's diff` banner when GitHub's diff differs.
- `summaries`: three to six sentences about the whole stack and one to three per PR, each with a button that shows the hunks it rests on under the sentence, on the canvas.
- `guide`: the whole stack's sections in reading order, each opening to its files, which open in their layer; Claude's when the repo allows it, Strata's groups otherwise.
- `mermaid`: "Copy as Mermaid" puts the map on the clipboard as a flowchart.
- `changes-api`: `GET /api/repos/:owner/:name/stacks`, `POST /api/changes`, `GET /api/changes`, `GET /api/changes/:id` and `POST /api/changes/:id/runs`. One Change per path: asking again for any PR on a path returns the same Change. While a repo's first read runs, the stack list and `POST /api/changes` answer `202 {"pending":true,"progress":...}` after 1.5 s; the same request asked again returns the latest step, then the result. The stack list holds only stacks with at least one open PR. It's kept under `<dataDir>/cache/stacks/` and answers at once after the first read, with `readAt`; once it's over 10 minutes old it still answers, with `refreshing: true`, while a new read runs behind it.

## How to get to it (user POV)

- On the home page, choose a stack under "Other stacks in <repo>", or a repo under "Stacks by repo" in the sidebar, or open `/repos/<owner>/<name>`. Choose Analyse on a stack.
- `POST /api/changes` with `{"input":"owner/repo#123"}` still makes the Change for any PR or branch.
- In a Change, choose a PR on the map, or "Whole stack" above it.

## Driving it with strata-verify

Preconditions:

- Stacks need GitHub data, and a plain `up` has none. Use one of:
  - `strata-verify up --github fixture` (no token, no network). A stand-in GitHub serves `acme/app`: a three-PR stack #9 → #10 → #11 where #10 is behind #9 and #11 is a draft; a fork #5 → {#6, #7}; a chain #1 → #2 → #3 whose bottom PR was squash-merged; a lone #4; and a fork-repo PR #8. It also has a branch with no PR, `inspect-demo`, for the inspect flags (`cli.md`). The rest of this recipe uses it.
  - `strata-verify up --github gh --checkouts GlyphicAI/maverick-backend=$HOME/workspace/maverick-backend` on the developer's Mac, for a real repo. It passes the token from `gh auth token` to the server's environment only. Compare what you see with the hand-written trees of the proving stacks.
- Run `doctor` and require exit 0. With the fixture it also checks the stand-in GitHub is alive.

API (`$B` is the RUN_ID):

- **List.** `strata-verify http $B stacks/list GET /api/repos/acme/app/stacks` returns 200 with three stacks, roots 9, 5 and 1 in that order. The #5 stack has `paths` `[[5,6],[5,7]]` and `defaultPath` `[5,7]`. #10 has `link` `"behind"`, a `needs-restack` issue and `linkEvidence` naming commits. #1 is `merged` with a `mergeCommitOid`.
- **Unknown repo.** `strata-verify http $B stacks/unknown GET /api/repos/acme/other/stacks` returns `502 {"error":"GitHub has no repo acme/other, or the token can't see it."}`.
- **Create.** `strata-verify http $B stacks/create POST /api/changes -H 'Content-Type: application/json' -d '{"input":"https://github.com/acme/app/pull/10"}'` returns 201 with `change.title` `"Cache forecasts per account"`.
- **Same path, same Change.** Repeat with `{"input":"acme/app#11"}`: 200 with the same `change.id`.
- **A fork's other path.** `{"input":"acme/app#5","leaf":6}` and `{"input":"acme/app#5"}` return two different ids.
- **Run result.** `strata-verify http $B stacks/detail GET /api/changes/<id>` shows `run.status` `"done"` (it goes from queued to done in about a second), `report.schemaVersion` `8`, `report.stack.selectedPath` `[9,10,11]`, `report.change.files` with `app/forecast_cache.py`, `app/jobs/warm_cache.py`, `migrations/0042_forecast_cache.sql`, `tests/test_warm_cache.py`, `uv.lock` and `web/admin/CacheStats.tsx`, `report.change.layers[].layer` `["data-model","logic","ui","tests","config"]`, `uv.lock`'s `mechanical.kind` `"lockfile"`, and `report.parts[].how` `["direct","replayed","replayed"]`. `POST /api/changes/<id>/runs` with `-d '{}'` returns 202 and a new run.
- **Bad input.** `{"input":"not a pr"}` returns 400 `Strata cannot read "not a pr"...`; `{"input":"acme/app#1,3"}` returns 400 `...is not a chain of branch links...`; `{"input":"acme/app@main...b4"}` returns 501.

## Gotchas

- The first request for a repo clones it into the instance's data folder. When that takes over 1.5 s, the stack list and `POST /api/changes` answer `202 {"pending":true,"progress":...}`: repeat the same request until it returns 200 or 201 (the web app does this each second and shows the step). On a real repo the first read can take minutes; pass `--checkouts` so Strata borrows objects from a local checkout.
- The fixture's PR timestamps are moved to the last hour at startup, so "updated 1h ago" is expected. Its commits have fixed authors and dates, so their ids are the same on every `up` (main at dd4a224, #3's head 709ec39), which [cli.md](cli.md) relies on.
- `?pr=<n>` with a PR outside the stack shows the whole stack rather than an error.
- The stand-in Claude's sentences are mechanical on purpose ("Changes <path>."). They test the plumbing: labels, dropping bad citations, the Guide's merge and order, and opening hunks. How good real answers are can only be judged with a real key on a real stack.
- With `--github gh`, the real repo's data stays on the developer's machine. Don't paste work titles or code into evidence you share outside it.
